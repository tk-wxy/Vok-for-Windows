## 详情

### §1 Vok 分层原生桌面架构与 .NET 10 基线

- **最终方案**：以 C#、.NET 10 LTS 和 WPF 为主技术路线。全屏主窗使用不透明普通 HWND，WPF 原生 Fluent 为默认视觉，WPF-UI 只允许隔离且可替换地使用。解决方案拆为 `Vok.App`、平台无关的 `Vok.Core`、`Vok.Infrastructure.Windows`、单元测试和 Windows 集成测试。单进程内由 WPF UI STA、热键消息线程、剪贴板 STA、Shell/COM STA、SQLite 执行器和有界图片 worker 显式拥有资源。数据采用 SQLite 可分页元数据与 `%LOCALAPPDATA%\Vok` 外置内容寻址资产。默认发布为自包含、非裁剪、非 Native AOT，其他优化按真实门禁启用。详细契约见 `docs/ARCHITECTURE.md`。
- **范围**：首期启动台、剪贴板、宿主显隐/焦点、必要设置与数据保护；同时约束后续中转站和搜索接入方式。
- **证据与根因**：Vok 的核心风险来自前台窗口限制、剪贴板/OLE/COM、全屏合成、长时间常驻和大数据量，而不是普通页面开发。`D:\dev\workbench-app` 的 Tauri/React/WebView2 实现被用户指定为性能反例且禁止复用代码；`D:\dev\vok(old)` 的实际 .NET 8/WPF 配置证明原生路线可行，但其分层全屏窗口、隐式通信、混乱模块边界和资源曲线也说明“换成 WPF”不足以保证轻量和可维护。2026-08-23 的官方资料显示 .NET 8 将于 2026-11-10 结束支持，.NET 10 LTS 支持至 2028-11-14；WPF .NET 10 已提供性能与 Fluent 改进。Microsoft.Data.Sqlite 的 Async 实际同步，WPF UI 虚拟化不等于数据虚拟化，`SetForegroundWindow` 也可能被系统拒绝，因此这些能力边界必须直接进入架构。用户于 2026-08-23 完全同意该分析与新方针。
- **否决方案**：继续以 .NET 8 开始绿地项目（支持期过短）；WebView2/Tauri/Electron（重复已知多进程、合成与时序代价）；仅因微软通用推荐而直接改用 WinUI 3（尚未证明 Vok 的隐藏、焦点、剪贴板和 OLE 高风险路径更优）；C++/Win32 全量 UI（维护和交互开发风险过高）；全屏 `AllowsTransparency=true`（不必要的分层合成成本）；单项目上帝组件、全局 Messenger、散落 `Task.Run`、JSON 全量存储或 EF Core（弱化所有权与规模控制）；提前使用 Native AOT/裁剪/单文件（WPF、XAML、COM/OLE 和发布兼容风险未验证）。
- **决定 / 最后验证**：2026-08-23 / 2026-08-23。
- **状态**：active；文档方针与 M0 宿主原型已落地，后续产品模块尚未创建。

### §2 产品参照边界与 M0 生产级宿主契约

- **最终方案**：`D:\dev\workbench-app` 是成熟功能与交互的主要产品形态参照，`D:\dev\vok(old)` 是已实现部分 WPF/Win32 行为的辅助参照；Vok 只研究并对齐两者的外部行为、交互流程、视觉结果与可运行性能，不复制、迁移或改写其代码。M0 定义为完整 Vok 的生产级宿主内核，本轮不实现 Launcher、Clipboard 或 Search 业务，但必须用可替换热键契约、长期存活的不透明 WPF HWND、代际化会话以及可观察的呈现/焦点结果闭环全屏显隐、真实输入焦点和关闭后的前台返还。窗口可见、会话期 Topmost、真实前台和 Win32/WPF 键盘焦点分别建模；当前 generation/Core 状态/五项结果与内部时间戳通过低频、seqlock 一致的 HWND 诊断属性对外直接观测，不解析 UI 文案。专用热键消息线程继续拥有 `RegisterHotKey`，除非实证表明它导致失败并经新决策改变。性能门槛只能在 Workbench、vok(old) 与 Vok 同机同条件数据形成后提出并由用户确认。
- **范围**：M0 宿主、热键、窗口呈现、焦点捕获/恢复、性能对照与验收；后续产品模块直接建立在该宿主之上。
- **证据与根因**：2026-08-24 用户明确确认两参照物的角色和上述 M0 定义。当前源码已经证明热键消息与全屏 HWND 创建可工作，但 `SWP_NOZORDER | SWP_NOACTIVATE` 后仅调用 WPF `Activate()` 会让窗口可见却仍在前台窗口之后；同时状态机在未观察真实前台/焦点时就完成 Show，诊断页的可聚焦 Grid 也不能证明未来搜索输入就绪。Workbench 的成熟外部形态同时暴露透明 WebView2 surface 在 native hide 后约 60–570ms 才重新出现、复杂轮询和高资源曲线；vok(old) 的 1:2:1 WPF 形态则暴露全屏 layered window、焦点轮询和复杂键盘 hook 的成本。因此必须保留产品行为，替换内部机制。
- **否决方案**：把 M0 当成会被推翻的诊断窗口；直接迁移两旧项目代码；永久 Topmost；把 Topmost 当成前台或焦点成功；为修复前台失败把热键无证据迁到 UI 线程；固定延时、焦点轮询、低级键盘 Hook、无限重试或默认 `AttachThreadInput`；在同机对照前自行发明最终性能数字；真实键盘、焦点往返和性能曲线未完成即进入 M1。
- **决定 / 最后验证**：2026-08-24 / 2026-08-24。
- **状态**：active；M0 核心宿主契约已于 2026-08-24 完成自动验证和真实物理键盘验收并冻结，后续 M1 直接复用该宿主。默认不使用 `AttachThreadInput` 仍成立，B 类例外见 §4。

### §3 M0 输入焦点锚点与 TextBox 资源边界

- **最终方案**：M0 的键盘测试区域使用真正可聚焦并接收 WPF `TextInput`/退格事件的宿主输入锚点，明确标注“非搜索功能”，不使用 WPF `TextBox` 冒充未来搜索。正式 Search 接入时必须把编辑、IME、可访问性、插入符与重复显隐资源作为独立纵向门禁。
- **范围**：M0 输入就绪证明、长期显隐资源；不决定未来 Search 的最终控件实现。
- **证据与根因**：2026-08-24 同机最小复现中，普通不透明空窗、全屏窗口、含未聚焦 TextBox 的窗口和每轮聚焦普通 Border 的窗口在 60 次 Show/Hide 后 GDI 均恒定；TextBox 一旦进入焦点生命周期则 GDI 从 15 每轮增长到 74。清除焦点、转移焦点、关闭首帧订阅、关闭诊断更新、关闭 Topmost 和跳过重复尺寸提交均未消除该曲线。这隔离出“TextBox 获得焦点后重复显隐与增长相关”的机制，但未识别具体 GDI 对象、WPF/TSF/IME/插入符所有权或回收条件，不能称为正式编辑器根因已修复。非编辑器锚点经 WPF STA 及外部同代五门禁直接验证，最终 1000 轮 GDI 峰值 17、斜率 0。
- **否决方案**：强制 GC；用透明 caret 或其他视觉常量遮盖；因 M0 需要输入证明就提前承担未闭环的搜索编辑器；删除真实 WPF 焦点验证；恢复旧版 cloak/layered window 来绕过资源曲线。
- **决定 / 最后验证**：2026-08-24 / 2026-08-24。
- **状态**：active；M0 的范围规避已完成 1000 轮宿主验证；中文 IME 与正式搜索编辑器语义及 TextBox 具体资源根因仍未验证。

### §4 B 类外部子焦点恢复的窄范围输入队列连接

- **最终方案**：保持“默认不连接输入队列”。只有隐藏已完成、Topmost 已清除、捕获顶层已经被最终观察为 foreground，但目标线程实际 `hwndFocus` 与同代 captured child 不一致时，才进入子焦点恢复。恢复前重新核验顶层和 child HWND 仍有效、进程/线程身份未变、child 仍是顶层本身或合法后代且属于目标线程；同线程直接 `SetFocus`，跨线程只将当前 WPF UI 线程与捕获目标线程连接一次，在 `try/finally` 中调用 `SetFocus(captured child)` 并尝试脱离。脱离后重新读取真实 foreground 与目标线程 focus；API 返回值不能替代最终结果。detach 失败单独报告并安全降级，不延时、不轮询、不模拟输入、不重复抢焦点。
- **范围**：M0 隐藏后的 B 类子控件焦点返还；不得用于掩盖顶层前台恢复失败、错误捕获、HWND 复用或迟到夺焦，也不自动推广到后续启动/粘贴链路。
- **证据与根因**：2026-08-24 的真实物理会话快照显示 generation 2 的捕获顶层和 focused child 均仍有效，PID/TID 与捕获时一致，child 仍为顶层合法后代；Vok 已隐藏且 Topmost/foreground/focus 标志清除，最终 foreground 等于捕获顶层，但目标线程 `GetGUIThreadInfo().hwndFocus=0`，状态为 `ForegroundConfirmedFocusChanged`。这将失败明确归入 B，而非 A/C/D。修复后 Release 构建零警告/错误、42/42 测试通过，用户分别确认快捷键隐藏和 Esc 隐藏后原文本框均可继续输入。
- **否决方案**：在顶层未恢复时对子 HWND `SetFocus`；全局或常驻 `AttachThreadInput`；跳过进程/线程/父子关系和 generation 校验；固定延时、轮询重试、模拟点击/按键或 Hook；把 attach/`SetFocus` 返回成功当作焦点已恢复；detach 失败后继续重复连接。
- **新增失败模式**：连接输入队列可能重置按键状态；目标线程可在校验后退出；child 可在调用前失效；`SetFocus` 或 detach 可失败。实现以单次尝试、`finally` 脱离、最终实测核验、显式状态和 Vok 始终保持隐藏/非 Topmost 限制影响。快捷键与 Esc 物理复验覆盖了常用修饰键释放及下一次普通输入，但不能消除所有 Windows 权限/线程终止边界。
- **决定 / 最后验证**：2026-08-24 / 2026-08-24。
- **状态**：active；作为 M0 冻结实现的一部分，未来变更须重新通过两种物理隐藏焦点返还回归。

### §5 目标显示器工作区窗口契约

- **最终方案**：Vok 呼出后占满既有目标显示器选择逻辑所确定显示器的系统工作区，窗口矩形完整采用 `MONITORINFO.rcWork`。任务栏必须保持可见且可点击，不推断或硬编码其高度与底部/顶部/左侧/右侧位置。会话期 Topmost、前台请求与观察、输入焦点门禁、隐藏及原目标焦点恢复机制均保持不变。
- **范围**：M0 窗口放置与产品布局契约；不引入设置、主题、快捷键录制或 M1 启动台业务。
- **证据与根因**：`rcMonitor` 表示完整显示器边界，不表达系统为任务栏和其他 appbar 保留的区域；继续用它会让工作台与任务栏争用同一矩形。Windows 已通过 `rcWork` 提供随任务栏边缘和工作区变化调整后的矩形，因此直接采用系统值可消除方向和厚度假设。2026-08-24 用户确认该产品契约；四种任务栏边缘的合成矩形测试、Release 构建和全套 46/46 自动测试已通过，用户真机确认任务栏交互、工作区铺满、两种隐藏焦点返还及视觉完整性正常。
- **否决方案**：硬编码任务栏高度或固定在底部；按 `rcMonitor` 放置后再用偏移修补；改变目标显示器选择；借布局调整改动 Topmost、前台、焦点或隐藏恢复链路；运行本轮明确排除的 1000 轮可见闪烁测试。
- **决定 / 最后验证**：2026-08-24 / 2026-08-24。

### §6 Visible 后丢失应用前台的被动关闭

- **最终方案**：完整格式目录中只要出现注册 `PNG`、`CF_DIBV5`、`CF_DIB` 或 `CF_BITMAP` 任一像素格式，就把本 sequence 归为 Image；随附 HDROP/Shell/HTML/URL 不抢占，也不在图片失败后跨类降级。没有像素格式而有有效 HDROP 才进入 FileList。Image 每次只复制一个候选：PNG 优先，否则 DIBV5，再否则 DIB；PNG 复制/超限/轻量 header preflight 失败时才在同次 OpenClipboard 尝试一个 DIB，已取得合法 PNG 后不为事后 codec fallback 复制 DIB。CF_BITMAP 只作来源信号并使用系统合成 packed DIB，不跨 CloseClipboard 借用 HBITMAP。`Vok.Image.Pixel.v1` 只含规范 RGBA 像素与尺寸，不含 DPI；有效 DPI 是 nullable replay metadata，缺失时约 96 DPI。首版上限为 input 192 MiB、单边 8192、40 Mi pixels、canonical 160 MiB、inline 2 MiB、copy buffer 1 MiB、worker 4 jobs、按 `input+canonical` 预留总计 384 MiB、thumbnail 512 px、thumbnail 编码长度不超过解码 BGRA8 字节加 1 MiB envelope、thumbnail cache 32 MiB。缩略图只按已布局展示槽与真实 viewport 加载，落地同时核验 entry/hash/entry+asset revision/当前 Recycling 容器；ViewModel 不持有图片源。Replay 仍从仓储取得轻量 descriptor；asset coordinator MTA 以稳定文件 lease 重做资产和像素身份校验，生成受限临时 DIBV5，materialization 独占 canonical/DIB 两个只读 blob。Clipboard STA 以 1 MiB buffer 顺序写 PNG、CF_DIBV5、marker，任一部分失败清除半份内容；图片主动作复用既有 `Materialize→Write→Hide/Restore→Verify→Inject` 状态机。
- **范围**：M2.3 图片/文件/文本路由、Clipboard STA 载荷裁剪、Inline/LeasedBlob、图片 worker 预留、Alpha/DPI 身份和后续 schema 5/replay；不决定 M2.4 保留总量或性能 SLA。
- **证据与根因**：Snipping Tool 区域/全屏与 QQ 图片都同时发布像素格式和 HDROP，证明“HDROP 绝对优先”会把图片误归文件；反例中 Explorer Ctrl+C 已知 PNG 文件只发布 Shell/HDROP，没有像素格式。Office 同次 PNG 865×541、DIB 554×346，证明多表示可冲突；QQ 无 PNG，证明 DIB 后备仍必需。浏览器受控 7680×4320 Alpha PNG 仅 1,334,507 bytes，但其 DIB/DIBV5 为 132,710,440/132,710,524 bytes；总是复制两种候选会无收益地增加约 126.56 MiB 载荷与持有剪贴板时间。全部真实 DIB DPI 为 0，受控源 PNG 的 96 DPI `pHYs` 又被 Chromium 丢弃，DPI 不具稳定身份。Windows 官方契约还规定 32bpp BI_RGB 高字节未使用，因此 Chromium 的孤立 Alpha mask 只能诊断；可信 Alpha 来自 PNG color type 4/6、合法 `tRNS` 或受支持 bitfields。M2.3.2 实测 WPF PNG encoder 即使 metadata 为 null 仍自动写 `pHYs`，故 canonical 输出必须流式剥离来源 metadata；系统合成 V5 会重复 header 中的 12-byte RGB masks，兼容只能以逐 mask 精确相等为条件。M2.3.4 进一步验证文件名 hash 不能代替落盘后复核，已存在同名未知内容必须拒绝覆盖；数据库事务不能与文件 rename 构成原子操作，故只能先提交并验证文件、再引用，失败方向固定为可复用孤儿文件而不是悬空引用。删除与重新引用跨越文件/数据库边界，必须由同一串行 coordinator 以 `(hash, revision)` 再认领，不能依赖易漂移 `ref_count`。M2.3.5 又实测无 Source 的 WPF `Image` 初次 `ActualWidth/Height=0`，以它自身尺寸判可见会形成永不加载的循环；固定展示槽的真实布局、先撤销绑定身份再取消和四维迟到核验才同时覆盖空卡、Recycling 串图与隐藏驻留。M2.3.6 验证“replay 失败”不是单一故障类：semantic/像素不一致必须 quarantine，但预取消、stale revision、暂存目录不可用或 writer 失败不能污染 Ready 资产；Win32 句柄在 `SetClipboardData` 成功前后所有权相反，必须以逐格式 transfer 状态收口。隔离 Window Station `reportVersion=5` 真实得到图片 receipt 当前、自写 SelfWrite 与外部覆盖失效。
- **否决方案**：HDROP 绝对优先；同时复制 PNG 与 DIB 作为无条件后备；把 HBITMAP 当 HGLOBAL 或跨关闭持有；信任 `BI_RGB` 的孤立 Alpha mask；把 DPI 放进像素哈希；沿用 64 MiB 单格式/16 项纯计数队列；无上限接受任意维度、profile 或图片 burst；分页后预载全部缩略图；App 拼 asset path；用空 Image 自身尺寸判可见；把 ImageSource 常驻 ViewModel；把原图读成大 `byte[]`；显式发布 CF_BITMAP；所有 replay 错误一律 quarantine；另建一套图片焦点/注入状态机。
- **新增失败模式**：合法 PNG header 仍可能在关闭剪贴板后 codec 失败，此时因单候选策略没有 DIB 后备；一个最坏 DIB job 会占大部分 384 MiB 预留，后续 burst 将明确过载丢弃；超过 8192 单边但总像素较小的超宽图也会拒绝；同像素不同 DPI 去重后 replay 物理尺寸不构成身份。文件已提交而数据库失败会留下无引用资产，等待同内容复用或 M2.4 清理；物理删除或最终 DB row 删除失败会留下 PendingDelete tombstone，启动重试；损坏文件保留为 Quarantined 证据。实现必须让这些结果可诊断，所有 reject/drop/cancel/exit 都释放 lease 与 reservation，且不得用提高上限、覆盖未知文件或跨类回退掩盖。

### §24 剪贴板保留、清空与资产回收事务

- **最终方案**：schema 6 在每条 `clipboard_entries` 保存可迁移回填的 `total_bytes`；保留计算把条目元数据字节与全局去重后的资产字节统一纳入受管总量。默认只保留最新 100 条未固定历史，未固定历史最长 30 天，受管总量最多 512 MiB；固定条目只豁免条数和时间规则，总容量到界时先淘汰最旧未固定项，仍超限才淘汰最旧固定项。自动保留、单项删除和清空都先在同一 SQLite 事务删除条目/引用并把零引用资产推进为带 revision 的 PendingDelete；同一个有界 MTA asset coordinator 再以 `(hash, revision)` 复核后删除文件与资产行，失败保留 tombstone 供启动重试。启动还只回收路径为 `xx/<64位小写SHA-256>.png`、且文件实际 SHA 与路径一致的 CAS 孤儿；未知或内容不符文件保留并报告。清空覆盖 Text/FileList/Image 全部历史，但不改系统剪贴板，也不删除 FileList 指向的用户文件。产品入口采用两次明确确认；清空 epoch 与捕获提交绑定，清空开始前的迟到捕获若已落库会再次按 ID 删除，不能在 UI 或重启后复活。
- **范围**：M2.4 schema 5→6、自动保留、固定语义、总字节计量、tombstone/孤儿资产回收、历史清空、缩略图缓存和捕获竞态；不改变 M2.3 单项图片安全边界、系统剪贴板内容或用户文件。
- **证据与根因**：SQLite 事务只能原子维护元数据，不能与 NTFS 文件删除组成同一事务；直接先删文件会在数据库提交失败时制造悬空引用，直接扫描资产目录并按文件名删除又会误伤未知内容。M2.3 已采用“文件先 Ready、数据库后引用”，其确定失败方向是可验证的无引用 CAS 文件，因此 M2.4 继续把数据库状态作为权威，并用 revision claim 和内容哈希证明回收资格。固定若无限豁免总容量，会使数据保护上限失效；只按条数又会让少量大图绕过边界。清空和正在进行的捕获若没有 epoch，会出现 UI 已空但旧捕获随后提交并在重启后重现。实现后的 schema 6 迁移失败测试证明版本与新增列同事务回滚；10,000 条元数据 keyset 分页、1,000 次连续捕获（监听持续响应且只留最新 100 条）、清空跨捕获竞态、固定/未固定淘汰顺序、全部类型清空、tombstone 重试、合法孤儿删除与伪装路径保留均有自动门禁。
- **否决方案**：按文件系统 mtime 或目录大小直接删 CAS；信任形似 hash 的文件名而不重算内容；维护易漂移的手工 ref_count；先删文件再提交数据库；固定条目无限突破总容量；只在 UI 隐藏旧捕获而不补删已提交行；清空同时清系统剪贴板或删除 FileList 源文件；在 WPF UI 线程扫描、哈希或执行 SQLite；用定时轮询、强制 GC 或进程重启代替有界回收。
- **新增失败模式**：清空/保留与捕获、重新引用或缩略图读取竞争；旧 revision 删除新资产；数据库已提交但物理删除失败；进程在 tombstone 后退出；未知文件伪装 CAS 路径；清空后迟到缩略图重新占用缓存；固定项使总量长期不降。实现用单 coordinator 排序、事务内零引用 claim、revision 再验证、启动恢复、实际 SHA 复核、缩略图 cache generation 和清空 epoch 限制影响；物理清理失败以 `AssetCleanupDeferred` 明确降级，不能冒充完全清理。

- **最终方案**：继续由 `H.NotifyIcon.Wpf` 拥有通知图标消息 HWND、鼠标事件与基础 Explorer 重建，不重写完整 `Shell_NotifyIcon` 宿主。Vok 以图标对象的实际 HWND/GUID 调用 `Shell_NotifyIconGetRect`，只有真实 Shell 查询成功才认为登记健康；启动、库内 `TaskbarCreated` 处理完成后、系统 Resume、会话 Unlock 都在 WPF UI STA 请求检查。低频 1 分钟 watchdog 只补漏系统事件，首次失败再于 250 ms 后复核；确定缺失后以单航班 `TryRemove → Create → Shell 后验查询` 修复，失败按 250 ms、1 s、3 s、10 s 有界退避，共最多五次。每轮以 generation 隔离迟到回调，原生菜单打开期间延后，退出先取消调度和静态系统事件订阅；耗尽后报告触发源、轮次和 HRESULT，并等待下一环境事件/watchdog，不无限忙重试。

- **证据与根因**：旧 PID 14120 已证明热键、WPF 主窗和 `H.NotifyIcon_*` HWND 可继续存活，而 Shell 对同一 GUID 的查询返回 `0x80004005`；进程内对象状态不是外部 Shell 登记。依赖库的 `Create()` 会在本地 `IsCreated=true` 时提前返回，`TaskbarCreated` 路径又吞掉 `TryRemove/Create` 异常，Vok 原先没有后验查询、Resume/Unlock 信号或失败重试，所以一次外部登记丢失会永久持续到重启。新集成测试直接原生删除测试图标登记，确认库仍报告 `IsCreated=true`，随后同 PID 自动恢复并通过 Shell 后验查询；故障注入另覆盖 watchdog 复核、五次耗尽、跨代迟到、菜单阻塞、Dispose、重入和“修复抛错但真实后验成功”。Release 65/65 Core + 364/364 Windows/WPF 共 429/429 通过。自包含 PID 28424 的真实登记随后被可逆删除，立即查询为 `0x80004005`，一分钟 watchdog 在不重启进程的情况下恢复为 `0x00000000`，`Ctrl+Space` 仍由该实例占有。
- **否决方案**：把进程/消息 HWND/`IsCreated` 存活当登记健康；依赖应用重启；只等待 `TaskbarCreated`；吞掉重建异常；无限或无后验查询的重试；把 1 分钟 watchdog 当同步完成条件；无证据升级预览包；在现有公开恢复接缝足够时重写完整通知图标消息宿主。
- **新增失败模式**：TaskbarCreated、Resume、Unlock 与 watchdog 同时触发；菜单嵌套消息循环中重建；上一轮 retry 在新一轮或 Dispose 后迟到；`TryRemove` 未获 Shell 确认但 Create 可继续；Create 抛错但 Shell 已部分成功；Shell 长期不可用。实现先占有状态再执行副作用，以单 Dispatcher scheduler、generation、菜单阻塞、后验结果优先、失败聚合和每轮有界次数限制影响。1 分钟/250 ms/退避序列是工程侧可调健康预算，不是产品语义或成功判据。
- **决定 / 最后验证**：2026-09-02 / 2026-09-02。
- **状态**：active；根故障机制、故障注入、真实 Shell 删除自愈、全量测试和自包含部署均已验证，用户反馈基础交互测试基本通过。真实 Modern Standby/睡眠、Unlock 与用户触发 Explorer 重启的物理事件矩阵尚未执行，不能由受控删除门禁或基础交互冒充。

### §26 剪贴板归档与中转站优先开发基线

- **最终方案**：M2.0–M2.4 以既定单屏范围归档并冻结；可复现故障、数据安全问题或经确认重开的专项之外，不再用非阻塞尾项延长剪贴板里程碑。后续路线先进入中转站纵向切片，再补齐剩余基础设置与数据保护界面。中转站先做产品契约与 Gate 0，再以文件引用形成最小端到端闭环；文本随后接入，图片必须等模块中立的资产引用与回收边界完成后再进入。剪贴板与中转站各自拥有聚合、持久化引用和生命周期，不建立通用内容业务表；SQLite 串行执行、内容寻址存储、有界 worker、分页/虚拟化和代次化动作只有在第二个真实消费者出现后，才提取为模块中立机制。窗口级外部 OLE 拖放继续由一个会话路由拥有，按目标模块分发，不能叠加互相竞争的租约。
- **范围**：M2 归档边界、M3/M4 顺序、中转站首个纵向切片和跨模块复用原则；不在本决策中锁定中转站最终视觉、完整 schema、容量数值、过期策略、拖出格式矩阵或图片实现细节，这些须由 Stage Gate 0 的证据决定。
- **证据与根因**：剪贴板归档复验通过 Release 65/65 Core + 364/364 Windows/WPF 共 429/429、8/8 PowerShell AST、clipboard probe report v7 扩展图片矩阵 20 轮和 win-x64 自包含发布，剩余真实清空、物理磁盘耗尽及跨屏/多屏均已被隔离为非阻塞专项。中转站与剪贴板都涉及内容展示、分页、排序、拖放和外置资产，但用户所有文件的引用生命周期与剪贴板历史的捕获/保留/自写抑制语义不同；直接共享 `Clipboard*` 模型会把两个领域耦合，而在第二消费者前抽象又无法证明接口边界。现有 `content_assets` 的回收只由 `clipboard_asset_refs` 证明引用，若中转站图片直接复用而不扩展全局引用判定，会错误删除仍被中转站使用的资产。启动台现有外部拖放租约同样是窗口级资源，平行增加 Stage 租约会造成终态清理和失活竞争。
- **否决方案**：继续用非阻塞物理尾项无限延长 M2；先完成所有设置再验证中转站核心体验；复制 `ClipboardEntry`/`clipboard_asset_refs` 作为中转站模型；预先建立包办文本、文件、图片和未来搜索的通用内容表；让启动台与中转站各自持有窗口级外部拖放会话；在未改造引用证明前让中转站图片直接进入现有 CAS 回收链。
- **新增失败模式**：共性提取可能破坏已冻结的剪贴板不变量；Stage 图片可能因跨模块引用漏算被回收；窗口级拖放可能跨目标区迟到或双重终结；路线切换可能被误读为已实现中转站。后续每步必须以 429/429 为回归底线，先写独立 Stage 合同和反例，再提取已被两个模块共同需要的最小机制；任何共享资产删除都必须证明所有模块引用为零，任何外部 OLE 终态都由单一会话所有者一次认领。
- **决定 / 最后验证**：2026-09-03 / 2026-09-03。
- **状态**：active；用户确认先完成剪贴板归档并提交，随后进入中转站开发基线。本决策只建立路线与边界，中转站业务代码尚未创建；当前交付顺序由 §28 进一步收窄。

### §27 中转站文件型产品契约与实施路线

- **最终方案**：将中转站定义为“引用型、可消费的临时货架”，首期一条文件/目录/`.lnk` 引用对应一张卡片，跨重启保存原始绝对路径、独立顺序和固定状态；不复制或接管源文件，`.lnk` 不静默解析成目标。同一 canonical path 再次拖入时在 SQLite 单事务去重并移动到本次位置；默认容量 50、首期产品上限 200，固定项同样计数，批量加入先扣除重复后整批接受或拒绝，不部分写入或静默淘汰。200 只作为组合根传入的产品策略，不进入数据库约束、仓储结构或分页契约；首版即使用 64 位计数、`(sort_order,id)` keyset、64 位稀疏排序和有界 VM 页面窗口，以 10,000 条门禁验证结构，后续提高到更高档位只调整策略并增加规模验证，不迁移 Stage 主结构或重写聚合。成功取用或 OLE 拖出只消费未固定项，“仅复制”、失败和取消保留；外部交付与内部清理分别记录，交付成功但 revision 冲突/清理失败时不得重放外部动作。入站和出站都只声明 `COPY`，出站目标返回 `Copy` 才算完成，任何 `MOVE` 歧义都不得删除源文件。Stage 拥有独立 Core 聚合、schema 7 `stage_items`、仓储、VM 和动作状态机；只复用现有 SQLite 执行器、Shell STA、Clipboard STA、输入注入和 Workspace 宿主事务。`MainWindow` 继续是唯一 `AllowDrop`，新增单一 `WorkspaceFileDropRouter` 路由 Launcher/Stage；Stage 拖出在 WPF UI STA 运行，先用隔离 Gate 0 证明 OLE 开始后的源窗隐藏、取消和资源闭环，WPF 路径不成立时才在同一 UI STA 窄封装原生 `DoDragDrop/IDropSource`。完整分期和验收见 `docs/M3_STAGE_PLAN.md`。
- **范围**：M3 文件型首个纵向切片的业务语义、容量/保留、schema 7、窗口级外部拖入、点击取用、Copy-only 拖出、排序/固定/移除、高上限兼容结构、实现顺序和验收门禁；不决定 Stage 文本/图片、多选、标签分组、搜索、自定义拖影、虚拟文件或跨设备能力。图片仍须在全局资产引用证明覆盖所有消费者后另行进入。
- **证据与根因**：Workbench 的外部行为证明“临时放入、跨窗口取用和拖出”的产品价值，但其内容混合与窗口自动关闭逻辑不能直接成为 Vok 的所有权模型。Vok 当前 `MainWindow` 只有一个窗口级 `AllowDrop` 且事件直接面向 Launcher；再增加平行 Stage 租约会让跨区域移动、DragLeave 缺失、隐藏和关闭发生双重终结。现有 `SqliteStorageExecutor`、`WindowsShellStaExecutor`、Clipboard STA、自写 receipt、`WorkspaceController` 目标恢复和 `IPasteInputService` 已提供所需底层资源所有者，复制线程或复用 `ClipboardEntry` 只会引入两套真相。OLE `DoDragDrop` 是带嵌套消息循环的 UI-STA 源事务，隐藏源 HWND 是否仍能稳定完成不能靠 API 推断，必须先以真实 Explorer/桌面目标验证。Stage 只保存用户文件引用，也没有剪贴板历史的捕获、自动保留和资产回收语义，因此应独立建表并把容量/去重/排序/消费置于同一 SQLite 权威事务。SQLite 索引和 keyset 足以承载远高于首期 200 的引用规模；真正会制造后续返工的是连续行号排序、滚动后永久累积 VM、启动全量检查和把 200 写入存储契约。剪贴板已有 keyset、外置 CAS 和有界缓存/worker，其高上限瓶颈是仓储内全量保留扫描与 UI 已加载页累积，可在现有仓储/UI 边界内替换，不要求合并领域模型。
- **否决方案**：复制 Workbench 代码或把 Stage 做成文件缓存；直接复用 `ClipboardEntry`、`ClipboardReplayPayload` 或 `clipboard_asset_refs`；Launcher/Stage 各持有窗口级 OLE 会话；在 `DragEnter/DragOver` 读取外部数据；使用 `COPY | MOVE` 并猜测终态；在成功拖出/取用前删除未固定项；固定项无限突破容量；批量超限时部分加入或淘汰旧项；把 200 写成 schema CHECK/仓储硬上限或窄字段；连续行号排序导致回顶/拖动全表更新；LoadMore 后永久保留全部 VM；启动时验证全部路径/图标；用固定延时猜测 OLE 已开始；把拖出放到 Shell STA 或新建 STA；在文件闭环前同时接入文本/图片和通用内容表。
- **新增失败模式**：首期产品上限可能被误当成永久架构上限；入站拖动跨区或缺失终态时视觉/lease 残留；Vok 的出站 FileDrop 被自身入站路由再次吞入；源窗隐藏终止 WPF 拖动或取消回调迟到；外部目标已接受但数据库消费失败；固定/revision 在外部动作期间变化；批量去重和容量检查竞争；路径失效、窗口换代、Clipboard receipt 被覆盖或输入注入受限。实现用产品策略/存储契约分离、10,000 条结构门禁、稀疏排序、有界页面窗口、唯一 router/source token、generation-scoped claim、一次性终态、WPF/OLE Gate 0、SQLite 单事务、expected revision、交付/清理双结果和现有目标恢复/receipt 门禁限制影响；任何外部副作用一旦完成都不得因内部清理失败而自动重试。
- **决定 / 最后验证**：2026-09-04 / 2026-09-04。
- **状态**：active；用户确认首期开发上限 200 合理，并要求当前架构预留后续高上限、避免再做高代价结构调整。产品合同与可扩容结构继续有效，当前交付顺序由 §28 修订为先完成入站 MVP；物理出站 WPF/OLE Gate 尚未实施且不再是当前前置步骤。

### §28 中转站先交付拖动呼出入站 MVP

- **最终方案**：不改变 §27 的完整文件型产品合同，但把当前可交付 MVP 严格收窄为一条入站链路：用户在 Explorer/桌面开始拖动文件、目录或 `.lnk`，用既有全局快捷键呼出 Vok，将指针移入中转站并松开；Vok 只快照一次 `FileDrop`，在 Shell STA 规范化后以 SQLite 单事务加入或去重回顶，随后展示并跨重启保留引用。当前 MVP 保留默认 50/首期上限 200、批量原子拒绝、64 位稀疏排序、keyset 和 10,000 条结构门禁，但不开放点击取用、仅复制、拖出、消费、固定、手工排序、打开/定位、移除或重新关联。`MainWindow` 仍是唯一 `AllowDrop`，现有 Launcher 入站处理收敛为唯一 `WorkspaceFileDropRouter`，Launcher/Stage 只作为目标 adapter，不各自拥有窗口级租约。§27 的隐藏源 HWND 出站 OLE 探针移到拖出功能之前执行，不再作为入站 MVP 的前置条件。
- **范围**：M3 当前最小可交付范围、实施顺序、外部拖动中呼出与 Stage 入站持久化；不撤销 §27 的完整功能语义和高上限契约，也不宣称后置的管理、取用、拖出或消费能力已经实现。
- **证据与根因**：用户于 2026-09-04 明确指定“中转站最小 MVP：拖动外部文件，呼出界面，在中转站松手，相关条目落入中转站”。源码核对显示 `MainWindow` 已是唯一 WPF `AllowDrop`，但其命中、视觉和分发目前直接绑定 Launcher；`WorkspaceController` 已用 Workspace generation 与真实 `DragEnter` lease 覆盖“拖着文件长按呼出”的松键、失活、Drop/取消和旧代竞态，且同一行为已在 Launcher 真机验收。因此入站 Stage 的未知量是统一目标路由、独立 Stage 持久化和展示，不是 WPF 作为 OLE 拖出源时隐藏 HWND 的可行性。若仍先做出站探针，会验证当前 MVP 不使用的机制并延迟最短用户价值链；若只做内存卡片，又无法证明“落入”能跨工作台隐藏和进程重启成立。

- **新增失败模式**：长按松键早于 DragEnter 时窗口可能按既有语义关闭；Launcher/Stage 跨区移动可能双亮或把 Drop 分发给旧目标；Drop 已向 OLE 返回 Copy 但异步规范化/落库失败；窗口因延后热键隐藏后成功/失败状态当次不可见；批量包含无效项时产品结果可能被误解为全部成功；重复回顶与并发容量检查竞争。实现以真实 DragEnter lease、单 router generation、Drop 终态冻结 target、先清视觉再单次快照、不可变路径消息、SQLite 单事务和可跨下次呼出保留的结果状态限制影响；OLE 接受和持久化成功必须分别表达，不能用 Copy 光标冒充落库成功。
- **决定 / 最后验证**：2026-09-04 / 2026-09-04。
