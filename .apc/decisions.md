## 详情

### §1 Vok 分层原生桌面架构与 .NET 10 基线

- **最终方案**：以 C#、.NET 10 LTS 和 WPF 为主技术路线。全屏主窗使用不透明普通 HWND，WPF 原生 Fluent 为默认视觉，WPF-UI 只允许隔离且可替换地使用。解决方案拆为 `Vok.App`、平台无关的 `Vok.Core`、`Vok.Infrastructure.Windows`、单元测试和 Windows 集成测试。单进程内由 WPF UI STA、热键消息线程、剪贴板 STA、Shell/COM STA、SQLite 执行器和有界图片 worker 显式拥有资源。数据采用 SQLite 可分页元数据与 `%LOCALAPPDATA%\Vok` 外置内容寻址资产。默认发布为自包含、非裁剪、非 Native AOT，其他优化按真实门禁启用。详细契约见 `docs/ARCHITECTURE.md`。
- **范围**：首期启动台、剪贴板、宿主显隐/焦点、必要设置与数据保护；同时约束后续中转站和搜索接入方式。
- **证据与根因**：Vok 的核心风险来自前台窗口限制、剪贴板/OLE/COM、全屏合成、长时间常驻和大数据量，而不是普通页面开发。`D:\dev\workbench-app` 的 Tauri/React/WebView2 实现被用户指定为性能反例且禁止复用代码；`D:\dev\vok(old)` 的实际 .NET 8/WPF 配置证明原生路线可行，但其分层全屏窗口、隐式通信、混乱模块边界和资源曲线也说明“换成 WPF”不足以保证轻量和可维护。2026-08-23 的官方资料显示 .NET 8 将于 2026-11-10 结束支持，.NET 10 LTS 支持至 2028-11-14；WPF .NET 10 已提供性能与 Fluent 改进。Microsoft.Data.Sqlite 的 Async 实际同步，WPF UI 虚拟化不等于数据虚拟化，`SetForegroundWindow` 也可能被系统拒绝，因此这些能力边界必须直接进入架构。用户于 2026-08-23 完全同意该分析与新方针。
- **否决方案**：继续以 .NET 8 开始绿地项目（支持期过短）；WebView2/Tauri/Electron（重复已知多进程、合成与时序代价）；仅因微软通用推荐而直接改用 WinUI 3（尚未证明 Vok 的隐藏、焦点、剪贴板和 OLE 高风险路径更优）；C++/Win32 全量 UI（维护和交互开发风险过高）；全屏 `AllowsTransparency=true`（不必要的分层合成成本）；单项目上帝组件、全局 Messenger、散落 `Task.Run`、JSON 全量存储或 EF Core（弱化所有权与规模控制）；提前使用 Native AOT/裁剪/单文件（WPF、XAML、COM/OLE 和发布兼容风险未验证）。
- **决定 / 最后验证**：2026-08-23 / 2026-08-23。
- **状态**：active；文档方针与 M0 宿主原型已落地，后续产品模块尚未创建。

### §2 产品参照边界与 M0 生产级宿主契约

- **最终方案**：`D:\dev\workbench-app` 是成熟功能与交互的主要产品形态参照，`D:\dev\vok(old)` 是已实现部分 WPF/Win32 行为的辅助参照；Vok 只研究并对齐两者的外部行为、交互流程、视觉结果与可运行性能，不复制、迁移或改写其代码。M0 定义为完整 Vok 的生产级宿主内核，本轮不实现 Launcher、Clipboard 或 Search 业务，但必须用可替换热键契约、长期存活的不透明 WPF HWND、代际化会话以及可观察的呈现/焦点结果闭环全屏显隐、真实输入焦点和关闭后的前台返还。窗口可见、会话期 Topmost、真实前台和 Win32/WPF 键盘焦点分别建模；当前 generation/Core 状态/五项结果与内部时间戳通过低频、seqlock 一致的 HWND 诊断属性对外直接观测，不解析 UI 文案。专用热键消息线程继续拥有 `RegisterHotKey`，除非实证表明它导致失败并经新决策改变。性能门槛只能在 Workbench、vok(old) 与 Vok 同机同条件数据形成后提出并由用户确认。
- **范围**：M0 宿主、热键、窗口呈现、焦点捕获/恢复、性能对照与验收；后续产品模块直接建立在该宿主之上。
- **证据与根因**：2026-08-24 用户明确确认两参照物的角色和上述 M0 定义。当前源码已经证明热键消息与全屏 HWND 创建可工作，但 `SWP_NOZORDER | SWP_NOACTIVATE` 后仅调用 WPF `Activate()` 会让窗口可见却仍在前台窗口之后；同时状态机在未观察真实前台/焦点时就完成 Show，诊断页的可聚焦 Grid 也不能证明未来搜索输入就绪。Workbench 的成熟外部形态同时暴露透明 WebView2 surface 在 native hide 后约 60–570ms 才重新出现、复杂轮询和高资源曲线；vok(old) 的 1:2:1 WPF 形态则暴露全屏 layered window、焦点轮询和复杂键盘 hook 的成本。因此必须保留产品行为，替换内部机制。
- **否决方案**：把 M0 当成会被推翻的诊断窗口；直接迁移两旧项目代码；永久 Topmost；把 Topmost 当成前台或焦点成功；为修复前台失败把热键无证据迁到 UI 线程；固定延时、焦点轮询、低级键盘 Hook、无限重试或默认 `AttachThreadInput`；在同机对照前自行发明最终性能数字；真实键盘、焦点往返和性能曲线未完成即进入 M1。
- **决定 / 最后验证**：2026-08-24 / 2026-08-24。
- **状态**：active；M0 核心宿主契约已于 2026-08-24 完成自动验证和真实物理键盘验收并冻结，后续 M1 直接复用该宿主。默认不使用 `AttachThreadInput` 仍成立，B 类例外见 §4。

### §3 M0 输入焦点锚点与 TextBox 资源边界

- **最终方案**：M0 的键盘测试区域使用真正可聚焦并接收 WPF `TextInput`/退格事件的宿主输入锚点，明确标注“非搜索功能”，不使用 WPF `TextBox` 冒充未来搜索。正式 Search 接入时必须把编辑、IME、可访问性、插入符与重复显隐资源作为独立纵向门禁。
- **范围**：M0 输入就绪证明、长期显隐资源；不决定未来 Search 的最终控件实现。
- **证据与根因**：2026-08-24 同机最小复现中，普通不透明空窗、全屏窗口、含未聚焦 TextBox 的窗口和每轮聚焦普通 Border 的窗口在 60 次 Show/Hide 后 GDI 均恒定；TextBox 一旦进入焦点生命周期则 GDI 从 15 每轮增长到 74。清除焦点、转移焦点、关闭首帧订阅、关闭诊断更新、关闭 Topmost 和跳过重复尺寸提交均未消除该曲线。这隔离出“TextBox 获得焦点后重复显隐与增长相关”的机制，但未识别具体 GDI 对象、WPF/TSF/IME/插入符所有权或回收条件，不能称为正式编辑器根因已修复。非编辑器锚点经 WPF STA 及外部同代五门禁直接验证，最终 1000 轮 GDI 峰值 17、斜率 0。
- **否决方案**：强制 GC；用透明 caret 或其他视觉常量遮盖；因 M0 需要输入证明就提前承担未闭环的搜索编辑器；删除真实 WPF 焦点验证；恢复旧版 cloak/layered window 来绕过资源曲线。
- **决定 / 最后验证**：2026-08-24 / 2026-08-24。
- **状态**：active；M0 的范围规避已完成 1000 轮宿主验证；中文 IME 与正式搜索编辑器语义及 TextBox 具体资源根因仍未验证。

### §4 B 类外部子焦点恢复的窄范围输入队列连接

- **最终方案**：保持“默认不连接输入队列”。只有隐藏已完成、Topmost 已清除、捕获顶层已经被最终观察为 foreground，但目标线程实际 `hwndFocus` 与同代 captured child 不一致时，才进入子焦点恢复。恢复前重新核验顶层和 child HWND 仍有效、进程/线程身份未变、child 仍是顶层本身或合法后代且属于目标线程；同线程直接 `SetFocus`，跨线程只将当前 WPF UI 线程与捕获目标线程连接一次，在 `try/finally` 中调用 `SetFocus(captured child)` 并尝试脱离。脱离后重新读取真实 foreground 与目标线程 focus；API 返回值不能替代最终结果。detach 失败单独报告并安全降级，不延时、不轮询、不模拟输入、不重复抢焦点。
- **范围**：M0 隐藏后的 B 类子控件焦点返还；不得用于掩盖顶层前台恢复失败、错误捕获、HWND 复用或迟到夺焦，也不自动推广到后续启动/粘贴链路。
- **证据与根因**：2026-08-24 的真实物理会话快照显示 generation 2 的捕获顶层和 focused child 均仍有效，PID/TID 与捕获时一致，child 仍为顶层合法后代；Vok 已隐藏且 Topmost/foreground/focus 标志清除，最终 foreground 等于捕获顶层，但目标线程 `GetGUIThreadInfo().hwndFocus=0`，状态为 `ForegroundConfirmedFocusChanged`。这将失败明确归入 B，而非 A/C/D。修复后 Release 构建零警告/错误、42/42 测试通过，用户分别确认快捷键隐藏和 Esc 隐藏后原文本框均可继续输入。
- **否决方案**：在顶层未恢复时对子 HWND `SetFocus`；全局或常驻 `AttachThreadInput`；跳过进程/线程/父子关系和 generation 校验；固定延时、轮询重试、模拟点击/按键或 Hook；把 attach/`SetFocus` 返回成功当作焦点已恢复；detach 失败后继续重复连接。
- **新增失败模式**：连接输入队列可能重置按键状态；目标线程可在校验后退出；child 可在调用前失效；`SetFocus` 或 detach 可失败。实现以单次尝试、`finally` 脱离、最终实测核验、显式状态和 Vok 始终保持隐藏/非 Topmost 限制影响。快捷键与 Esc 物理复验覆盖了常用修饰键释放及下一次普通输入，但不能消除所有 Windows 权限/线程终止边界。
- **决定 / 最后验证**：2026-08-24 / 2026-08-24。
- **状态**：active；作为 M0 冻结实现的一部分，未来变更须重新通过两种物理隐藏焦点返还回归。

### §5 目标显示器工作区窗口契约

- **最终方案**：Vok 呼出后占满既有目标显示器选择逻辑所确定显示器的系统工作区，窗口矩形完整采用 `MONITORINFO.rcWork`。任务栏必须保持可见且可点击，不推断或硬编码其高度与底部/顶部/左侧/右侧位置。会话期 Topmost、前台请求与观察、输入焦点门禁、隐藏及原目标焦点恢复机制均保持不变。
- **范围**：M0 窗口放置与产品布局契约；不引入设置、主题、快捷键录制或 M1 启动台业务。
- **证据与根因**：`rcMonitor` 表示完整显示器边界，不表达系统为任务栏和其他 appbar 保留的区域；继续用它会让工作台与任务栏争用同一矩形。Windows 已通过 `rcWork` 提供随任务栏边缘和工作区变化调整后的矩形，因此直接采用系统值可消除方向和厚度假设。2026-08-24 用户确认该产品契约；四种任务栏边缘的合成矩形测试、Release 构建和全套 46/46 自动测试已通过，用户真机确认任务栏交互、工作区铺满、两种隐藏焦点返还及视觉完整性正常。
- **否决方案**：硬编码任务栏高度或固定在底部；按 `rcMonitor` 放置后再用偏移修补；改变目标显示器选择；借布局调整改动 Topmost、前台、焦点或隐藏恢复链路；运行本轮明确排除的 1000 轮可见闪烁测试。
- **决定 / 最后验证**：2026-08-24 / 2026-08-24。
- **状态**：active；代码、自动门禁和用户真机验收均完成。
